# PX915 Road Network Junction Model — Progress Summary & Design Reference

> **Purpose of this document**: context for future development sessions. It records not just what was built but *why* each design decision was made, where the subtle bugs were, and what invariants must be preserved when extending the code.

---

## Project Context

University of Warwick group project (Tristan McCarthy, Jasper Allen, Stephan Gambert, Lucas Belz-Koeling). Deadline: 28 May 2026.

The core model is a **1D TASEP** (Totally Asymmetric Simple Exclusion Process) — a cellular automaton where particles hop right with probability 1, enter at site 1 with probability α, and exit at site L with probability β. This models single-lane traffic flow. The network extension adds junctions so multiple roads can interact.

**Existing code is untouched**: `tasep.f90`, `simulation.f90`, `io.f90` are the original single-lattice model and must remain unchanged. All new code is in separate modules compiled alongside.

## Architecture Overview

```
vehicle_mod          — integer cell codes (V_EMPTY, V_STRAIGHT, V_LEFT, V_RIGHT)
road_network_mod     — data types: lane_t, road_t, junction_t, road_network_t
network_init_mod     — hard-coded crossroad builder (init_crossroad)
junction_mod         — evaluate_junctions and all right-of-way logic
network_simulation_mod — network_step driver + lane_internal_step
```

These five modules depend on each other strictly in the order listed above. No circular dependencies.

## ⚠️ Critical Design Invariants (read before touching any module)

### 1. Clockwise Array Rule
Junctions store `connected_road_ids(:)` in **strict clockwise order**. In the crossroad: 1=N, 2=E, 3=S, 4=W. All directional logic — destinations, yield-to-right, opposite leg — is **pure modulo arithmetic on array indices**. There are no string labels or compass-direction conditionals anywhere in the model code (only in the human-readable test printout).

**Why**: makes the code generalise to any N-leg junction without rewrites. The modulo formulas are:

| Turn | Destination index `dst_k` |
|------|--------------------------|
| STRAIGHT | `mod(k + N/2 − 1, N) + 1` |
| LEFT (UK easy turn) | `mod(k, N) + 1` |
| RIGHT (cuts across oncoming) | `mod(k + N − 2, N) + 1` |
| Right-of-i (R1 target) | `mod(i + N − 2, N) + 1` |
| Opposite-of-i (R2/R3, N=4 only) | `mod(i + 1, N) + 1` |

**UK driving convention**: LEFT is the easy swing (clockwise next leg); RIGHT cuts across oncoming traffic. This is the opposite of the US convention. Getting this wrong breaks the yield rules.

### 2. Lane Orientation
- `lane(1)` carries flow **end₁ → end₂** (vehicle index increases toward end₂)
- `lane(2)` carries flow **end₂ → end₁** (vehicle index increases toward end₁)

For a junction at road end `e` (1 or 2):
- **Inbound lane** (toward junction) = `3 - e` — always has the holding cell at site **L**
- **Outbound lane** (away from junction) = `e` — always receives arriving vehicles at site **1**

In the crossroad all roads connect at end 1, so inbound = lane 2, outbound = lane 1. **Do not hardcode this assumption** — always call `inbound_lane_idx(end_at(k))` and `outbound_lane_idx(end_at(k))`.

### 3. Parallel-Update Ordering
Every timestep runs in this exact order:
```
snapshot_network      ← copies cells → old for ALL roads/lanes
evaluate_junctions    ← reads old, writes cells
lane_internal_step    ← reads old, writes cells
```
**Both** junction and lane steps read from `old` (the frozen snapshot). This is the fundamental parallel-update invariant: no vehicle can react to another vehicle's move within the same timestep.

Consequence: a vehicle placed at site 1 of an outbound lane by the junction this step will NOT be moved again by `lane_internal_step` this step (because `old(1)` is still V_EMPTY). It sits at site 1 until the next step.

### 4. Full-Step Yield Semantics
If vehicle A must yield to vehicle B, A waits the **entire timestep** — even if B also moves this step. The yield check is:
```fortran
yields_live = any(yields_to(i, :) .and. (holding /= V_EMPTY))
```
It checks `holding` (the old snapshot), not whether B was approved. **This is intentional.** It prevents the approve_pass from cascading (where A sees B approved and tries to move into B's vacated spot in the same step).

## Phase 1 — Data Structures

### `vehicle.f90` — cell state encoding

Every cell in the entire network holds one integer. That integer encodes both whether a vehicle is present and what it intends to do at the next junction:

- `V_EMPTY = 0` — no vehicle
- `V_STRAIGHT = 1` — vehicle going straight through
- `V_LEFT = 2` — vehicle turning left (UK easy turn, no cross-traffic)
- `V_RIGHT = 3` — vehicle turning right (cuts across oncoming)

Intent is assigned **at lane entry** by `sample_indicator(p_left, p_right)` and stays with the vehicle for its entire journey down the inbound lane. This avoids having to store intent separately and keeps occupancy checks trivially fast (`cell /= 0`).

### `road_network.f90` — data types and utilities

Defines the four types that everything else is built on:

- **`lane_t`**: one unidirectional 1D TASEP lane. Holds `cells(:)` (current state), `old(:)` (snapshot for parallel update), and boundary parameters (`alpha`, `beta`, `p_left`, `p_right`, `open_in`, `open_out`).
- **`road_t`**: a bidirectional road — simply a container for two opposite `lane_t`s, plus `end_junction(2)` recording which junction (if any) connects at each end.
- **`junction_t`**: a node where roads meet. Stores `n_legs`, `connected_road_ids(:)` (clockwise), and `end_at(:)` (which end of each road touches this junction).
- **`road_network_t`**: the top-level container — allocatable arrays of `road_t` and `junction_t`.

Also provides three utilities used throughout:
- `inbound_lane_idx(e)` / `outbound_lane_idx(e)` — convert a junction end-number into a lane index.
- `snapshot_network(net)` — copies `cells` into `old` for every lane; called once at the start of each timestep.
- `count_occupied_network(net)` — counts total vehicles across all cells; used by the integration test.

### `tests/test_types.f90` — Phase 1 validation

**What it does**: allocates a full `road_network_t` manually (4 roads × 2 lanes × 100 cells), checks the occupancy predicate on known values, then calls `sample_indicator` 10,000 times with a seeded RNG and counts outcomes.

**What it prints**:
```
P(left)= 0.2495  P(right)= 0.2503  P(straight)= 0.5003
test_types: OK
```

**What passes**: `is_occupied(V_EMPTY)` returns false, `is_occupied(V_LEFT)` returns true, and the sampled indicator distribution matches the expected probabilities within ±2%. Exits 0 on success, stop 1 on any failure.

## Phase 2 — Crossroad Initialisation

### `network_init.f90` — building the test network

`init_crossroad(net, L, alpha, beta, p_left, p_right)` builds the standard 4-road crossroad used in all subsequent tests. Concretely:
- Allocates 4 roads and 1 junction.
- Junction leg ordering: 1=N, 2=E, 3=S, 4=W (clockwise). All roads connect at their end₁.
- Each road gets two lanes of length L, initialised to all V_EMPTY.
- Lane 2 (inbound, site 1 at the open boundary): `open_in=T`, alpha, p_left, p_right set.
- Lane 1 (outbound, site L at the open boundary): `open_out=T`, beta set.

`free_network(net)` deallocates all allocatable arrays. **Always call this at the end of a test** — gfortran doesn't complain but Valgrind will.

### `tests/test_init_crossroad.f90` — Phase 2 validation

**What it does**: calls `init_crossroad`, then programmatically checks every structural property of the resulting network.

**What it prints**:
```
Crossroad layout (clockwise):
  road 1  N  end_a -> junction
  road 2  E  end_a -> junction
  road 3  S  end_a -> junction
  road 4  W  end_a -> junction
  inbound lane = 2 (site L = junction holding cell)
  outbound lane = 1 (site 1 = junction destination)
test_init_crossroad: OK
```

**What it validates**: `size(roads)==4`, `size(junctions)==1`, `n_legs==4`, `connected_road_ids==[1,2,3,4]`, `end_at==[1,1,1,1]`, `end_junction==[1,0]` on every road, all cells V_EMPTY, all lane lengths correct, `open_in`/`open_out` flags set on the right lanes, and that `inbound_lane_idx`/`outbound_lane_idx` return 2 and 1 respectively for end=1.

## Phase 3 — Junction Evaluation

### `junction.f90` — the right-of-way engine

This is the most complex module. The right-of-way logic proceeds in seven steps inside `evaluate_one_junction`:

**Step 4 — Yield matrix (`build_yield_matrix`)**

Three rules applied in sequence, building `yields_to(i,j)` = "leg i must yield to leg j":

- **R1 (yield-to-right)**: `yields_to(i, right_of_i) = T` if `paths_conflict(N, holding(i), holding(right_of_i), delta=3)`. Conflict is TRUE unless both are V_LEFT.
- **R2 (right-turn yields oncoming)**: if leg i is V_RIGHT, it yields to its opposite leg if that leg is V_STRAIGHT or V_LEFT.
- **R3 (opposite-leg delta=2 scan, N=4 only)**: for each pair (i, opp) not already resolved by R1/R2 — if (S, L): left yields to straight; if (L, S): left yields to straight; if (R, R): mutual yields → will become deadlock.

**`paths_conflict(N, ti, tj, delta)`** — pure function:
- delta=1 or delta=3: conflict unless both V_LEFT
- delta=2 (opposite): no conflict if (S,S) or (L,L); conflict otherwise

**Step 5 — Approval pass (`approve_pass`)**

A vehicle is approved if: has vehicle, destination is phys_clear, and `yields_live = any(yields_to(i,:) .and. holding/=V_EMPTY)` is FALSE. The `holding /= V_EMPTY` check (not `.not. approved`) is essential for full-step yield semantics.

**Step 6 — Deadlock breaker (`resolve_deadlocks`)**

A vehicle is "in deadlock" if:
1. It yields to at least one non-approved, non-deadlocked vehicle, AND
2. **It yields to NO already-approved vehicle** ← this second condition was added to fix the mass conservation bug (see Phase 5).

```fortran
in_deadlock = any(yields_to(k,:) .and. (holding /= V_EMPTY) &
                  .and. .not. approved .and. .not. deadlocked) &
              .and. .not. any(yields_to(k,:) .and. (holding /= V_EMPTY) &
                             .and. approved)
```

One winner is picked stochastically from the deadlock set. All others are marked `deadlocked` for this timestep — the `deadlocked` flag prevents the cascade where multiple iterations keep picking more winners from a ring.

### `tests/test_junction.f90` — Phase 3 validation

**What it does**: nine self-contained subtests. Each one calls `init_crossroad` with alpha=beta=0 (no boundary flow, so only the junction logic runs), manually places vehicles in specific holding cells, calls `snapshot_network` then `evaluate_junctions`, and inspects the result. A fixed RNG seed (42) makes stochastic tie-breaks reproducible.

**What it prints** (one line per subtest, then a final ALL OK):
```

  test_single_move OK
  test_physical_block OK
  test_yield_right OK
  test_right_turn_yields OK
  test_parallel_opposite_straight OK
  test_parallel_left_left OK
  test_mutual_right_deadlock OK
  test_4way_straight_deadlock OK
test_junction: ALL OK
```

**What each subtest validates**:

| # | Name | Setup | Assertion |
|---|------|-------|-----------|
| 1 | `test_dest_math` | Calls `compute_destination` for all 12 (leg, intent) combinations | Results match the hand-worked modulo table (e.g. leg 1 STRAIGHT → road 3, leg 1 RIGHT → road 4, leg 1 LEFT → road 2) |
| 2 | `test_single_move` | One V_STRAIGHT in leg 1 holding cell | Holding cell cleared; road 3 outbound site 1 filled |
| 3 | `test_physical_block` | V_STRAIGHT in leg 1; road 3 outbound site 1 pre-filled | Neither cell changes — physical block prevents the move |
| 4 | `test_yield_right` | V_STRAIGHT in legs 1 and 4 (W is to the right of N) | Leg 4 advances; leg 1 stays — yield-to-right rule |
| 5 | `test_right_turn_yields` | V_RIGHT in leg 1, V_STRAIGHT in leg 3 (oncoming) | Leg 3 advances; leg 1 stays — R2 rule |
| 6 | `test_parallel_opposite_straight` | V_STRAIGHT in legs 1 and 3 | Both advance in the same step — parallel through-traffic does not conflict |

Exits 0 if all pass, stop 1 on the first failed assertion.

### Bugs fixed in Phase 3 (before integration)

| Bug | Symptom | Fix |
|-----|---------|-----|
| Missing R3 scan | Mutual right-turn deadlock never triggered; both vehicles approved | Added the delta=2 opposite-leg scan to `build_yield_matrix` |
| `approve_pass` cascade | After one vehicle approved, others whose yield-target was now "approved" also got approved | Changed yield check from `.not. approved(j)` to `holding(j) /= V_EMPTY` |
| No `deadlocked` flag | 4-way standoff resolver picked multiple winners in successive loop iterations | Added `deadlocked(:)` array; marks all non-winners, prevents re-selection |

## Phase 4 — Network Simulation Driver

### `network_simulation.f90` — timestep driver

Exposes two public routines:

**`network_step(net)`** — advances the entire network by one timestep. Internally calls the three sub-phases in order: `snapshot_network` → `evaluate_junctions` → `lane_internal_step`.

**`lane_internal_step(net)`** — the TASEP update for every lane in the network. For each road × lane:
1. **Exit at site L** (only if `open_out=T`): reads `old(L)`, clears `cells(L)` with probability beta. This is the open boundary outflow.
2. **Bulk hops** (sites L-1 down to 1): if `old(i) /= EMPTY` and `old(i+1) == EMPTY`, the vehicle hops — `cells(i+1)` gets the vehicle, `cells(i)` cleared. Reads entirely from `old` so hops are strictly parallel (a vehicle moves at most one site per step).
3. **Inflow at site 1** (only if `open_in=T`): reads `old(1)`; if empty, tries to inject a new vehicle with probability alpha. Intent is assigned by `sample_indicator`. This is the open boundary inflow.

The `open_in`/`open_out` flags ensure lane roles don't overlap with the junction: inbound lanes skip the exit (junction handles it); outbound lanes skip the inflow (junction places vehicles there).

**`run_network(net, n_steps, entries, exits)`** — multi-step driver. Runs `n_steps` calls to `network_step` and counts cumulative entries (new vehicles at inbound site 1) and exits (vehicles leaving outbound site L) per road. Used for computing steady-state currents.

## Phase 5 — Integration Soak Test & Mass Conservation Bug

### `tests/test_network_run.f90` — integration validation

**What it does**: builds a crossroad with L=20, α=0.4, β=0.5, p_left=p_right=0.25. Runs 500 burnin steps (discarded — allows the network to reach steady state), then 5000 production steps with two checks:

1. **Per-step mass conservation**: at every step, counts entries (inbound site 1 was empty before, non-empty after) and exits (outbound site L was non-empty before, empty after) and asserts `n_after == n_before + entries - exits`. If this fails, it prints the exact step number, counts, and stops immediately.

2. **Steady-state symmetry**: after 5000 steps, prints the cumulative entry/exit counts and mean currents per road, then asserts that the maximum per-road exit current is non-zero and that the ratio `(max - min) / max < 0.20` (20% tolerance). Because the crossroad is geometrically symmetric, all four roads should carry similar traffic.

**What it prints on success**:
```
PASS: mass conservation OK (all 5000 steps)

--- Per-road outbound currents ---
 Road  Entries  Exits  J_in   J_out
    1    1353    1335  0.2706  0.2670
    2    1364    1351  0.2728  0.2702
    3    1321    1388  0.2642  0.2776
    4    1372    1335  0.2744  0.2670
Exit current range:  0.2670 - 0.2776

PASS: per-road currents are non-zero and symmetric
test_network_run: ALL OK
```

**What it prints on failure**: the step number, n_before, step_entries, step_exits, expected and actual counts, then stop 1. This makes the failing step trivially identifiable for debugging.

### Debugging process that led to the final fix

**Step 1 — wrong baseline**: the original test captured `n_initial=0` before burnin, so 500 steps of vehicle accumulation made the final count look wrong. Rewritten to capture `n_before` after burnin and check per step.

**Step 2 — isolating the phase**: per-step check failed at step 173. Added a debug subroutine that counted vehicles after each sub-phase:
```
before snapshot  =  64
after junctions  =  63   ← vehicle lost here
after lane_step  =  63
```

**Step 3 — finding the overwrite**: injected a detector into the commit loop that printed whenever it was about to write to a non-empty destination cell. Confirmed two approved vehicles both writing to road 4, lane 1, site 1.

**Step 4 — tracing the logic failure**:
- Leg 3 (V_LEFT) had no yield targets → approved in the first pass.
- Leg 1 (V_RIGHT) yielded to leg 3 by R2 (right-turn yields to oncoming left) **and** to leg 4 by R1.
- The deadlock resolver saw leg 1's yield to leg 3 as "cleared" (leg 3 was approved, so `.not. approved(3)` = false). Only leg 4 was still blocking leg 1.
- Leg 4 was blocked by approved leg 3, so it was not "in deadlock" either.
- The resolver declared leg 1 the sole deadlock member and approved it — **overriding its outstanding yield to already-approved leg 3**.
- Both committed to the same destination. One vehicle was destroyed.

**Fix**: a candidate only enters the deadlock set if it yields to **no** already-approved vehicle — one extra boolean condition added to `in_deadlock`. If any yield target is already approved, the candidate simply waits this step (it was always going to lose that interaction; the deadlock machinery should not override it).

### Final results

All 9 Phase 3 unit tests still pass after the fix. Integration test: 5000 steps, zero mass violations, per-road currents vary by ≈4% (well within the 20% tolerance). All four executables build with **zero warnings** in the new modules.
